psxrecomp · SLUS-00662 · field notes

Why the Parasite Eve recomp ran slow

The static recompilation booted fine but ran at roughly 0.7× speed — menus, FMVs, and gameplay all sluggish. This is what the instrumentation showed, the one change that moved the needle to ~0.8×, and why the four follow-up tests all came up empty.

host  i7-6700HQ · 4C/8T · 2015 mobile gpu  GTX 1070 · ~idle · 1× scale bios  retail SCPH-1001 (US) target  59.94 Hz NTSC · 33.8688 MHz

The short version

Parasite Eve streams almost all of its logic — menus, rooms, battles, cutscenes — as code overlays loaded from the disc at runtime. psxrecomp only translates the main executable ahead of time; overlay code runs in one of three tiers: static native, compiled-on-first-sight native, or the dirty-RAM interpreter.

The scaffold-generated game.toml never enabled overlay caching, so 100% of overlay code was interpreted. Turning it on exposed a second problem: the bundled clang toolchain can't compile overlay shards. With a real GCC in place, overlays compiled — but one function stayed stuck in the interpreter and accounted for nearly the entire remaining cost.

Root cause

0x80191B94 — RoomLib_InitD in the decomp — sits in Parasite Eve's resident room-library overlay, which is loaded during essentially all field play and menus. Its overlay compiled to a native DLL, but the runtime's capture never tagged this address as a function entry, so it fell back to the interpreter forever: 383 million interpreted instructions, ~26,000 per entry.

Forcing the compiler to carve it out (compile_overlays.py --force-interior 0x80191B94) dropped the interpreter's share of every frame from ~41% to ~4%.

How we got there

  1. Symptom

    Recomp builds and boots. Steady ~0.72–0.80× speed, dropping to ~0.22× in some scenes. An earlier macOS build had a similar issue fixed by disabling vsync.

  2. Ruled out vsync & pacing

    PSX_VSYNC=0 — the macOS fix — had no effect. The wall-clock pacer measured correct at 16.6611 ms/frame (≈ 60.02 Hz vs NTSC 59.94).

  3. Ruled out the FMV decoder

    Menus were slow too, and there was no MDEC activity during the slow spans. Not an FMV-specific problem.

  4. Root cause: overlays interpreted

    game.toml was missing [runtime] overlay_cache = true. Every overlay ran on the interpreter, the slowest tier. Added that plus idle_skip = true.

  5. Toolchain blocker

    The bundled clang pack fails every overlay shard with a hard cannot add 'dllexport' attribute error — clang-only, no downgrade flag. Installed WinLibs GCC 16.1.0.

  6. Overlays compiled — still slow

    With real GCC, 16 overlay DLLs built cleanly. Speed nudged up but held ~0.72×, still sagging to 0.22×.

  7. Instrumented

    Built a RelWithDebInfo runtime with the debug TCP server on :4370, ran stall_report.py for interpreter/exception attribution.

  8. Diagnosis

    ~40% of every frame was the interpreter, and ~99% of that was one address, 0x80191B94. Cross-referenced against the decomp: RoomLib_InitD, an “interior fragment” the overlay compiler never exposed as a callable function.

  9. Fix applied

    --force-interior on that address plus three other observed hot PCs, wired into build\play.ps1.

  10. Result

    Interpreter share 40.8% → 4.1%. Native-overlay share 3.1% → 23.0%. Release-build speed stabilized at ~0.80× — and stopped collapsing to 0.22×.

  11. Tested: OpenBIOS vs retail

    A/B on the debug build. Exception handling stays ~20–22% of the frame either way; OpenBIOS is marginally slower. The kernel cost is not a BIOS-choice problem — retail stays the right pick.

  12. Tried: force every overlay function

    Patched compile_overlays.py to read a 1,131-address file of every decomp overlay function. It backfired — a background-compile storm (237 half-built DLLs) dragged speed to ~0.19×. Reverted to an opt-in flag; the targeted hot set is the working config.

  13. Tried: -march=native

    Rebuilt with Skylake AVX2/FMA codegen (-march=native -O3, verified in the compile flags). No measurable change — menus/field held ~0.79× either way. The frame is scalar recompiled game code plus the LLE kernel; neither vectorizes.

  14. Not available: PGO

    The psxrecomp_cli.py rebuild --force-pgo path passes -DPSX_PGO=, but this framework pin has no such CMake option — the flag is silently ignored, so there is no instrumentation to profile. Profile-guided optimization would need patching the framework's build files.

What the decomp actually does here

The recompiler works straight off the retail disc — disc → recompiler → C → native binary. It never reads decomp C. The decompilation is a reference layer bolted alongside, and it is easy to over-credit it:

decomp inputs · fed in by bridge/decomp_bridge.py
InputConsumed byEffect on the build
symbols.toml — 1,674 names, all emit = falseheader generation onlyNone. Naming. It is why 0x80191B94 reads as RoomLib_InitD.
seeds/ghidra_funcs.txt — 1,300 probe + 1,736 from decompthe recompiler, as function-start hintsAdditive. More complete function carving; more likely to help coverage than hurt.
--force-interior addressescompile_overlays.pyThe four that matter came from stall_report. The decomp only labeled them.

The three real problems — overlay_cache off, clang can't build shards, one overlay function interpreted — are none of them decomp-caused. A pure no-decomp recomp hits all three the same way, just with worse names.

What changed on disk

Everything below is local build config — none of it is committed upstream to parasite-eve-recomp or parasite-eve-decomp.

# parasite-eve-recomp/game.toml — [runtime] overlay_cache = true # capture + compile overlays instead of interpreting idle_skip = true # fast-forward guest spin-waits
  • build/play.ps1 — launch wrapper: overlay autocompile via WinLibs GCC, --force-interior hot set, FPS telemetry, --no-launcher, -OpenBios flag for A/B.
  • bridge/decomp_bridge.py — the decomp→recomp bridge, generalized past Parasite Eve (see the table above).
  • compile_overlays.py patched with fromfile_prefix_chars='@' so a force-interior address list can be passed as a file.
  • WinLibs GCC 16.1.0 at %LOCALAPPDATA%\Programs\mingw64\ — the bundled clang pack cannot build overlay shards.
  • Two builds: build-release/ (37.5 MB, what you play) and build-dbg/ (163 MB, RelWithDebInfo, debug server on :4370).

Where it stands — the levers are spent

The --force-interior fix handled the single biggest cost. Everything on the follow-up list has now been tried, and none of it moved the needle further.

  • testedKernel / exception overhead (~22%)

    OpenBIOS vs retail made no difference — the LLE kernel's interrupt and syscall dispatch is ~20–22% of the frame on both. Inherent to a cycle-faithful LLE BIOS. Reducing it would mean trading emulation accuracy for speed (PSX_EVENT_STEP_*) — out of scope.

  • triedThe per-room overlay tail

    Forcing every decomp overlay function (1,131) caused a compile storm. The path that works is growing the -ForceInterior set from per-area stall_report output, or a curated RoomLib subset — slow, incremental, worth chipping at.

  • tried-march=native rebuild

    Applied cleanly (-march=native -O3). No measurable change — the workload is scalar recompiled game code and the LLE kernel, neither of which vectorizes.

  • n/aPGO

    Not implemented in this psxrecomp framework pin — the CLI's -DPSX_PGO is silently ignored. Would require patching the framework's CMake.

Where it actually lands

Menus and field play hold ~0.79× (about three-quarters of the time in an unattended session). FMV and heavy scripted scenes drop to ~0.25×. It hit exactly 1.00× at boot, and the native parts of the frame run at full speed — so it is not a raw hardware wall, but the practical ceiling on this box is ~0.8×, set by the two structural costs that stayed put: the interpreted RoomLib tail and the LLE kernel.

That is fine for the actual goal — the recomp is the platform for mod work, where 0.8× is workable and the decomp→symbol bridge is what matters. For playing Parasite Eve through, DuckStation runs it at full speed on the same machine.

The bottleneck is one CPU core

This machine is a well-specced 2016 gaming laptop — 48 GB RAM, a GTX 1070, an NVMe SSD. None of that touches this workload. Faithful console emulation is a single-thread CPU race, and the CPU is the one component that is a 2015 mid-range mobile part.

what each component does while the recomp runs
ComponentRole in this workload
48 GB RAMWorking set is ~1–2 GB. Capacity does nothing for CPU-bound work.
GTX 1070 (8 GB)~99% idle. PS1 graphics at native resolution are trivial — the GPU is never the limit.
Samsung 990 PRO NVMeSpeeds the disc read and shard compiles. Zero effect on the per-frame simulation.
i7-6700HQDoes ~100% of the work, on roughly one core. The entire constraint.

The i7-6700HQ's gaming reputation came from the discrete GPU it was paired with. The CPU itself is a 4-core Skylake part from 2015, and Intel's mobile single-core performance barely moved for years afterward. Emulation lives or dies on exactly that number.

"but Task Manager only shows ~17% CPU"

Because it averages one saturated thread across eight logical cores. Thread-level, over a 4-minute session: the emulation thread burned 215 CPU-seconds of 246 wall-seconds — ~90% of one core, continuously — while the whole process totalled 0.95 cores. Windows migrates that hot thread around all eight cores every few milliseconds, so no single core's graph ever reads 100%, but the critical path is one pegged core.

Pinning the process to 2 cores changed nothing (0.775× → 0.77×); pinning to 1 core made it worse (0.27×), because the present and audio threads need a second core to run alongside. There is no idle capacity to recruit and no migration cost to remove.

Same single-threaded work, roughly 2× the core speed — so the fanless MacBook Air has headroom to spare and the 2016 gaming laptop does not. A Steam Deck, a recent phone, or any modern desktop CPU closes the same gap. The recompiled game code needs the equivalent of only ~1.3–1.5 GHz sustained on a current core to lock 60; this CPU delivers about 0.8 of that.
