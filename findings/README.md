# Findings

Perf + framework-bug investigation from running Parasite Eve Recompiled from
source on a 2015 laptop (i7-6700HQ). Same five findings, four formats for
four different uses:

**Recompiler vs. game, at a glance**: every performance finding below
(findings 1-5, the RoomLib fix, and the FMV dispatch-overhead finding) is a
`psxrecomp` recompiler/tooling issue — the original Parasite Eve code is
unremarkable in every case, and no decomp change is implicated. The one
exception is `video-bleed-through-splash.md`, whose root cause points at
the original game's own code (or possibly a subtle difference in how
psxrecomp tears down an interrupted video versus real hardware) — see that
doc for the caveat that this hasn't been confirmed against real hardware.

| **`savestate-restore-lazy-revalidation-race.md`** | **Root-cause found for the visual-corruption half of the finding above.** Quoted directly from the runtime's own code and comments: every savestate restore deliberately bumps every overlay page's generation counter and force-invalidates every cached-valid candidate (`overlay_watch_invalidate_after_ram_restore`/`overlay_loader_resync_validation_after_restore`) — a real, by-design guard whose own comment names "hang / freeze after the restored frame presents" as the exact failure class it exists to prevent. This makes the earlier "revalidation storm" **not a bug** — it's the expected one-time cost of every resident candidate legitimately re-checking itself once. The real gap: revalidation is *lazy* (on next dispatch, one candidate at a time), so the very first frame after a restore can draw with a not-yet-rechecked candidate before the guard has had a chance to run — a precise explanation for "corrupted once, clean on an immediate second load," matching everything observed live and confirmed independent of LTO. The document's own LTO-performance hypothesis was written before a matched retest — **that retest (see the FMV brief's Follow-up 5) found no LTO-specific performance effect at all**, so the "why is LTO slower" section is superseded; only the visual-corruption mechanism stands as a confirmed finding. ## The five findings, briefly

1. The bundled `cmake-clang-v1` toolchain can't compile a single overlay
   shard (`dllexport` redeclaration clang treats as a hard error) — every
   player on it runs 100% interpreted overlays, permanently, across every
   psxrecomp title.
2. A captured overlay can silently lose a function entry the capture doesn't
   classify as a boundary, and the auto-compile path has no fallback for it
   — one such entry cost ~40% of the frame here.
3. `PSX_PGO` is passed to CMake but consumed by nothing — `rebuild
   --force-pgo` / the launcher's "Optimize FMV" is a silent no-op.
4. The from-source project scaffold (`probe_disc.py`) never sets
   `overlay_cache = true` — a from-source build interprets 100% of overlays
   until that's added by hand.
5. Not a bug: a clean single-core compute wall on 2015-era CPUs, with one
   accuracy-neutral mitigation suggested (sim-protecting frame skip).

Findings 1, 3, and 4 are verified identical in `mstan/psxrecomp@master` and
`RetroPortingToolKit/psxrecomp@master` — upstream bugs, not fork drift from
the `Alexbeav/psxrecomp` pin this project actually builds against.
